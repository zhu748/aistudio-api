# 酒馆工具历史丢失与冷缓存差异

## 提交演变与原始错误

原始错误是 `Function call is missing a thought_signature in functionCall parts`，不能与后续 `Requests ending with a model turn are not supported` 混为同一根因。

逐版本离线重放同一份客户端原文（各版本使用独立空缓存）得到：

| 版本 | 变更 | 实际保留的原生调用 | 转换后收尾 |
|---|---|---|---|
| `46f5139` 的父提交 | 尚未引入签名剥离 | 两次 `context` 与一次 `soliumbra_reply` | 工具结果所在 user 轮 |
| `46f5139` | 按工具名剥离无签名的“服务端工具”及结果 | 仅 `soliumbra_reply` | model 轮，含空轮 |
| `21c2feb` | 缓存回注；未命中时扩大为剥离所有工具调用及结果 | 无 | model 轮，含空轮 |
| `70f7f4c` | 删除全空轮，合并相邻同角色轮 | 无 | 仅剩 `user → model` |
| `7c30736` | 为 model 收尾追加单空格 user 轮 | 无 | `user → model → user(" ")` |

因此模型结尾错误是处理签名问题时删除历史产生的副作用，不能反推客户端原本启用了 assistant prefill。最早提交将 `default_api:context` / `context` 认作上游 Saved Info 工具，并假设剥离结果不损失对话语义；但本例客户端明确声明了自己的 `context` 函数，工具结果就是完整上下文。`21c2feb` 的提交说明也已承认 `default_api:` 命名空间会出现在客户端声明函数的报错中，不能凭此前缀认定为内置工具。

上面的重放验证转换行为，不声称重新进行了各历史版本的真实上游请求。原始缺签名问题、后续空轮/模型收尾错误、HTTP 200 下的上下文丢失应分别验证。

## 已复现的原因

同一份 OpenAI 客户端原文经过旧版转换代码时：

| 签名缓存状态 | 上游 contents | 请求体字节数（现场快照） |
|---|---|---:|
| 冷缓存 | `user → model → 单空格 user`，工具调用和结果被删除 | 5,393 |
| 缓存已有 `context` 的真实签名 | 两组 `context` 调用及结果恢复；其他未命中工具仍被删除 | 121,886 |

用第二次客户端原文离线重放，冷缓存下的 `contents` 与第一次上游快照完全相等；将第一次响应的 `context` 签名加入缓存后，再次转换的 `contents` 与第二次快照完全相等。第二次两处 `context` 历史使用的签名也确实等于第一次响应中的签名。

客户端最后一条实际为 `role=tool`，不是 assistant prefill。旧逻辑在缺少可用 thought signature 时删除了 tool call 及配对 result，导致原本放在工具结果中的世界设定与当前状态丢失，剩余历史才变成 model 收尾，触发单空格 user 占位。用户已确认两次是相同输入的重 roll；第一份未保存，无法独立逐字比对，但同一份原文的离线复现精确解释了两个上游历史的差异。

第一次上游返回的是 `context({"query":"sync"})` 函数调用，随后正常结束，并非 `sync` 正文被网络截断。上游没有生成正式回复；客户端如何显示函数参数需要结合客户端日志判断。

第二次能生成正文也不代表历史完整：现场客户端中另一工具的约 6.2 万字符历史参数及对应结果仍因缓存未命中而被删除。

## AIStudio2API 对照与当前修复

对照版本：[Mag1cFall/AIStudio2API `ef6fbbce7eda4e00d27493e0df7915dbf2d8c896`](https://github.com/Mag1cFall/AIStudio2API/tree/ef6fbbce7eda4e00d27493e0df7915dbf2d8c896)。

- `internal/aistudio/request.go` 的 `encodePart`：原生调用缺少签名时写入 `skip_thought_signature_validator`，`setPartThoughtSignature` 将其原样置于槽位 14，不做 Base64 编码。
- `internal/api/thoughtsig.go`：按调用 ID、函数名和规范化参数恢复真实签名，不按函数名跨调用借用。
- `internal/aistudio/compatibility_test.go` 的 `TestFunctionCallThoughtSignature`：断言缺失签名时槽位 14 为该字面量、已有签名原样保留。
- 同一 `request.go` 的 `linkFunctionResults`：正常配对结果保留原生结构，只有关联不到调用的孤立结果才转为文本。

据此替换了本地上一版的默认文本降级方案：

- 保留调用、参数、ID、配对结果及附带图片；仅孤立/乱序结果保留为文本。
- 客户端已携带有效签名或特殊占位值时优先原样使用；兼容 `thought_signature` / `thoughtSignature` 两种签名键。
- 缓存只对调用 ID、函数名、规范化参数均一致的调用恢复真实签名；未命中时补特殊字面量，避免历史随冷/暖缓存而消失。
- 占位值不当作真实签名缓存；旧的按名称/ID 缓存记录无法确认参数，不再恢复。新缓存按调用指纹存储，不保存参数原文，使用私有权限原子写入。
- 清理真正的空轮、对真正的 model 收尾做兼容的逻辑保留；正常以工具结果结束的预设不会因签名丢失而变成 model 收尾。

这一选择基于对方实际源码、自带测试及用户在同一预设下的成功报告；本地测试验证的是完整转换与 wire 槽位，不冒充使用真实 Google 账号重发成功。前面的历史实验只测过随机 Base64 伪签名，没有测这个有明确协议含义的特殊字面量，不能据此断言它也会被拒绝。

回归测试使用合成世界设定与历史，覆盖 OpenAI、Claude、Responses、Gemini 的冷/暖缓存，以及无 ID、乱序结果、图片和签名别名。真实用户附件不纳入仓库。

## 后续移植：完整模型轮与轮次令牌

继续对照同一参考提交的 `model_turns.go`、`request.go`、`generate.go` 和工具流实现，补齐了这些机制：

| 机制 | 当前实现 |
|---|---|
| 完整模型轮恢复 | 保存上游 Part 顺序，包括思考、函数调用及独立签名载体；客户端回传同一回复时恢复原始 wire Part |
| 匹配前序对话 | 累积摘要包含前序用户文本、工具调用名与规范化参数、工具结果；忽略客户端省略的思考与签名，允许合并/拆分相邻模型轮 |
| 调用 ID 改写 | 匹配后沿用客户端回传的 ID，确保后续结果仍能关联；调用顺序、参数和正文变动会使恢复失效 |
| 并发隔离 | 相比参考实现的 API key 范围，额外绑定上游账号、模型、系统指令及工具配置；客户端明确回传不同真实签名时保持该状态 |
| 轮次令牌 | 随历史中最后一个匹配模型轮恢复；遇到后续未知模型轮则清空，移除原有账号级共享令牌缓存 |
| 生命周期与容量 | 只保存正常 STOP 的完整响应；失败、取消、截断、媒体及服务端工具结果不保存；每次重试独立采集，限制 1000 条、总计 64 MiB、单轮 4 MiB 和 Part 数量 |
| 工具结果配对 | ID 优先；元数据缺失时按唯一待返回调用或同名调用补齐；明确冲突 ID、跨过新用户轮的旧调用、孤立结果保留为文本，不删除结果内容 |

恢复先于 WAA proof 生成，签名计算和实际发出的 contents 使用同一份历史。缓存仅在当前进程存活，不将整轮对话写入磁盘。MIT 版权说明保留于 `src/aistudio_api/THIRD_PARTY_NOTICES.md`，随 Python 包分发。

流式参数合并、重复调用检测、参数大小限制与异常结束时阻止执行残缺调用继续使用本项目现有实现；对方源码明确说明其上游 functionCall 整体到达，不能用该假设替换本项目已有的碎片兼容。

本轮新增跨四种接口、流式/非流式的两阶段往返验证，以及重 roll、并行调用、缺失元数据、调用 ID 改写、不同客户端/账号/模型/指令、异常响应与容量边界测试。真实 Google 上游未在本环境复测；旧文档中的活体验证不代表本轮修改已经完成活体复测。

## 验证记录

- `uv run pytest -q --tb=short`：1277 passed、5 skipped；跳过的都是缺少 Go 编译工具链的真实桥接集成测试。前置检查现在也识别“同名 go 程序并非编译器”的情况。
- Ruff 检查、格式检查和 `bun x pyright src tests` 通过。Python wheel 构建确认包含第三方版权说明。
- 用户提供的原始请求再次离线重放：3 次调用与 3 组结果的载荷逐一验证完整保留；无关签名缓存不影响转换结果。只输出结构统计，不将用户原文加入仓库。
- 全量检查发现原有 1.5 MB 图像解析的 20 ms 护栏在当前环境重复超时。将字符串内的正则字符类扫描替换为 `str.find`，缓存下一个引号位置，避免转义密集时反复扫描尾部。保持原有 20 ms 阈值不变；同机 7 次采样中位数为旧实现 12.14 ms、新实现 2.63 ms，输出相等，转义密集字符串与既有分块测试通过。
